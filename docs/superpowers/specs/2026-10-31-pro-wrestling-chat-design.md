# プロレスチャット 設計

## 目的

チャットで遊ぶ、ソロプレイ用・1対1・ターン制のプロレスゲーム。
一番の価値は **小説のような描写の読み応え**。駆け引きはその物語を支える骨格として扱う。

AI は同じような出力を繰り返しがちなので、展開を分ける要素（敵の行動選択・成否判定・空欄設定の補完）には必ず乱数を通す。

## ゴール / 非ゴール / アンチゴール

ゴール

- 1試合 5 分程度（体力 5、概ね 3〜6 ターン）で、毎回違う展開になる
- 地の文・実況・解説のセリフで、試合を小説のように描写する
- ログインしたユーザーごとに試合履歴を保存し、途中で閉じても再開でき、終わった試合も読み返せる

非ゴール

- ガードレール（入力フィルタ・安全対策）。ローカル利用が前提のため扱わない
- 対人戦、マルチプレイ、デプロイ
- 体力の初期値の変更 UI（固定値 5）

アンチゴール（動いても失敗とみなすもの）

- 敵が毎ターン同じ技・同じ種類を使い続ける
- AI が体力計算や相性判定をして数値を間違える
- 描写が箇条書きや短いログのようになり、読み物にならない

## 技術構成（決定済み）

- Next.js 16.4.3（App Router）、bun。既存の create-next-app の雛形を土台にする
- Mastra は Next.js の Route Handler 内に組み込み、1 プロセスで動かす
- libSQL（ローカルファイル）に BetterAuth のテーブル、Mastra のストレージ（ワークフローのスナップショット）、アプリの試合データを保存する
- BetterAuth はメール + パスワード
- UI は shadcn/ui + AI Elements
- モデルは最新の Gemini Flash 系。モデル ID は実装時に gemini-api-dev skill で確認する
- リポジトリの `.claude/skills` に各ライブラリの skill がある。Next.js 16 は学習データと API が違うので、`node_modules/next/dist/docs/` を読んでから書く（AGENTS.md）

## 役割分担：コードと AI

| 担当 | 内容 |
|---|---|
| コード（決定論） | 相性判定、成功率、乱数の実行、ダメージ計算、体力更新、決着判定、状態の保存 |
| AI（Gemini） | 技の分類（種類・格）、敵の発生率テーブルの作成、空欄設定の肉付け、敵タイプの推定、情景と結果の描写、決着方法の選択 |

AI には数値の更新をさせない。AI の出力は構造化出力（スキーマ付き）で受け取り、コードで検証する。

## 乱数発生スキル

- Mastra の `createTool` で作るツール。重み付きの候補表を受け取り、`node:crypto` の乱数で 1 つ選んで返す
- 戻り値には、引いた値と選ばれた候補を含める（デバッグ表示に使う）
- コード側の判定（成功率の判定など）も、同じ関数を直接呼ぶ。乱数の実装は 1 か所にまとめる

## 試合の状態（構造体）

ワークフローが保持し、毎ターン libSQL に保存する。最低限:

- `setting`: 場面（時刻・場所）、プレイヤー設定、敵設定、敵タイプ（巨漢 / スピード / マッチョ / 技巧派）
- `player` / `enemy`: `hp`, `maxHp`（どちらも初期値 5）
- `turn`: ターン番号
- `status`: `in_progress` | `finished`
- `winner`, `finish`（決着方法）: 終了時に設定
- `log`: 各ターンの分類・発生率テーブル・乱数結果・判定結果（デバッグ表示と読み返し用）

## 試合の流れ

### 1. 状況設定（フォーム）

新規試合の画面に、項目ごとのフォームを出す: 場面（時刻・場所）、プレイヤーの設定、プレイヤーの得意技（任意）、敵の設定。

- 空欄は AI がランダムに補完する。似た設定ばかりにならないよう、コードが乱数ツールで「種」（時間帯、会場の種類、レスラーの年齢・キャラ・ヒール/フェイスなどの候補表から 1 つずつ）を引き、AI がそれを肉付けする（候補表の中身は実装者の判断）
- 敵タイプは、敵の設定文から AI が推定する。判断が付かなければ乱数ツールで 4 種から選ぶ。敵の設定が空欄なら、乱数で選んだタイプに合わせて AI が設定を作る

### 2. 初期化

プレイヤー・敵の体力を 5、最大体力を 5 にする。

### 3. ターン（Mastra Workflow のループ。プレイヤー入力で suspend / resume する）

1. **敵の行動を選択**
   - AI が、体力、有利不利、情景、敵の性格とタイプから、技の種類ごとの発生率テーブルを作る。技の格（通常 / 大技 / 必殺技）の発生率テーブルも作る
   - タイプごとの傾向: 巨漢 → 投げ技、スピード → 飛び技、マッチョ → 打撃技、技巧派 → 極め技
   - コードがテーブルを検証してから乱数ツールで種類と格を引き、AI がその種類・格に合う具体的な技名を決める
   - 偏り防止:
     - どの種類にも最低限の発生率を残す（下限値は実装者の判断）
     - 直前のターンと同じ種類は、コード側で発生率を下げてから乱数を引く（係数は実装者の判断）
     - それまでに敵が使った技名を AI に渡し、同じ技名を避けさせる
2. **情景の解説**: プレイヤー、敵、観客の状態を、地の文・実況・解説のセリフで描く。敵が選んだ行動は名指しせず、予兆としてそれとなく描写に混ぜる（読み合いの手がかり）
3. **プレイヤーの行動入力**（ここで suspend）: 自由文で技や動きを書く
4. **行動の判定**
   - AI がプレイヤーの入力を種類（投げ / 極め / 打撃 / 飛び）と格（通常 / 大技 / 必殺技）に分類する
     - 格は技名と動きの大きさから AI が判定する。「必殺技を出す」のような自己申告では決めない。設定で登録した得意技に当たる場合は必殺技とする
     - 回避・挑発・様子見など攻撃でない入力は「技なし」とする。プレイヤー側は判定に進まず、敵の技だけを成功率で判定する。描写は入力の意図に沿って書く
   - 相性: 投げ > 打撃 > 極め > 投げ。飛び技は相性を持たない
   - **相性で決まる場合**: 勝った側の技だけが判定に進み、負けた側の技は潰される
   - **相性で決まらない場合**（同じ種類同士、どちらかが飛び技）: 双方の技をそれぞれ成功率で判定する。両方成功なら相打ちで両者ダメージ、両方失敗ならダメージなし
   - 成功率は、技を受ける側の残り体力の割合で決まる。技をかける側の体力は影響しない

     | 受ける側の残り体力 | 通常 | 大技 | 必殺技 |
     |---|---|---|---|
     | 60% 超 | 90% | 50% | 20% |
     | 30% 超〜60% | 95% | 70% | 45% |
     | 30% 以下 | 100% | 90% | 70% |

     （数値は実装者の判断として決めた初期値。定数 1 か所にまとめる）
5. **結果の描写と反映**: ダメージは通常 -1、大技 -2、必殺技 -3。コードが体力を更新したあと、AI がその結果を小説的に描写する
6. **決着の判定**: どちらかの体力が 0 以下になったら試合終了
   - 決着方法は AI が状況から選ぶ（ギブアップ、3 カウント、場外負けなど）。最後に決まった技が極め技ならギブアップを基本にする
   - 相打ちで両者が同時に 0 以下になった場合は、乱数で勝者を決める（実装者の判断）
   - 終了ターンの出力末尾に `<<END>>` を付け、状態の `status` を `finished` にする

## 画面

- `/login`: メール + パスワードのサインアップ / ログイン
- `/`: 自分の試合一覧（進行中 / 終了）と「新しい試合」ボタン
- `/matches/new`: 状況設定フォーム
- `/matches/[id]`: 試合のチャット画面
  - 上部に常時表示する体力バー（プレイヤー / 敵、現在値 / 最大値）
  - 中央は AI Elements の会話表示。描写はストリーミングで表示する
  - 下部に行動入力欄。試合終了後は入力欄を閉じ、決着を表示する
  - 進行中の試合を開くと、それまでの描写を表示し、入力待ちから再開する

（URL 名は実装者の判断）

## デバッグモード

- サーバー側の環境変数（例: `DEBUG_MODE=true`）でオン / オフする
- オンのときだけ、サーバーがデバッグ情報をクライアントに送る。UI に、敵が選んだ行動、発生率テーブル、乱数の結果、プレイヤー入力の分類、成功率、状態の構造体（JSON）を表示する
- オフのときは、敵の行動などをクライアントに一切送らない（予兆の読み合いが成立するように）

## テスト

- 相性判定、成功率の選択、ダメージ計算、決着判定は純粋関数にして、`bun test` で単体テストを書く
- 乱数は差し替えられるようにして、テストで結果を固定する

## 実装者に任せること

- Mastra ワークフローの具体的なステップ分割、ストリーミングの実装方法
- libSQL のアプリ用テーブル設計（試合とターンの保存形式）
- プロンプトの文面（日本語、小説調、実況・解説のセリフを含む）
- 画面のデザイン詳細
