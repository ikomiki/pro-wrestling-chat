# 語り手への状況リスト化・セリフ中心の文体・処理中表示 設計

## 目的

narrator が前の場面の文章に引っ張られ、同じ描写を繰り返している。前の文章を渡すと、言い回しや展開をそのまま引き継いでしまうためである。

そこで narrator には過去の文章を一切渡さず、その時点の状況を要素の箇条書きで渡す。あわせて次の 2 点を行う。

- 文体をセリフの多いライトノベル寄りにし、差し替え用の文体見本（Few-shot）を入れる。
- AI が考えている間の待ち時間に、いまの処理名を画面に出してストレスを減らす。

判断の経緯と選ばなかった案は `akapen/narration-situation-01.html` にある。

## ゴール / 非ゴール / アンチゴール

ゴール

- narrator の入力に、過去に生成した文章が一切含まれない。
- 前の場面とのつながりは、状況リストと出来事の事実だけで保たれる。
- 描写の中で、プレイヤー・敵・実況・解説の 4 者がセリフを話す。プレイヤーの心の声は `（）` で書かれる。
- 文体見本は独立したファイルにあり、ユーザーが中身を差し替えるだけで文体を変えられる。
- AI の処理中は常に、いまの処理名が 1 行表示される。

非ゴール

- 文体見本の文章の質。仮の文章を置き、ユーザーが自分の文体に差し替える。
- 旧形式の試合データとの互換。

アンチゴール

- 画面に、敵が次に出す技名や、状況リストの生データ（`situation`）がそのまま出てしまう（ネタバレ）。描写の中で敵が意気込みを語るのは構わない。
- 状況リストを入れたことで、体力や確率の数値が描写に漏れる。

## 決定事項

### 1. 状況リスト（MatchState に追加）

`matchStateSchema` に `situation` を追加する。各項目は 1 文の文字列で、次の 7 つ。

| キー | 内容 |
|---|---|
| `crowd` | 観客と会場の様子 |
| `position` | リング上の位置関係 |
| `momentum` | 試合の流れ（どちらが押しているか） |
| `playerMind` | プレイヤーの心境 |
| `playerPlan` | プレイヤーの行動方針（AI の推測） |
| `enemyMind` | 敵の心境 |
| `enemyPlan` | 敵の行動方針 |

- **初期値:** 試合の設定を作る analyst の呼び出し（`setupStep` の `completeSetupPrompt`）の出力に、初期値も含めて出させる。
- **更新:** 判定の後に 1 回だけ行う（ユーザー決定 Q1=A）。
  - `resolveStep` で `resolveTurn` と決着の仕方の決定（勝者が出たとき）を終えたあとに、analyst を新しく 1 回呼ぶ（`situationPrompt`）。
  - narrate はその後に実行する。
  - analyst には、更新前の状況リスト、そのターンの判定結果、プレイヤーの入力文、両者の体力の状態（言葉で）を渡す。
- `sceneStep` では状況を更新しない。前のターンで判定の後に作った状況をそのまま使う。

### 2. narrator への入力

`lastNarration` と、`narratorSituation` の `prev` 引数（直前の描写の全文）を廃止する。保存した文章（messages テーブル）は表示と履歴のためだけに使い、AI の入力には戻さない。

場面のプロンプトも結果のプロンプトも、次の見出し付きの箇条書きで組み立てる。

```
## 設定
- 時間 / 場所
- プレイヤー: 名前（説明）状態: 体力を言葉にしたもの
- 敵: 名前（説明）タイプ / 状態
## いまの状況
- 状況リストの 7 項目
## これまでの出来事
- ターンごとに 1 行。state.log から AI を使わずに作る
## この場面で描くこと
- 場面: 敵が狙う技（技名・種類は書かず予兆だけ）。初回なら入場とゴングから
- 結果: 判定、受けたダメージを言葉にしたもの、プレイヤーの入力文、決着
```

- 「これまでの出来事」の 1 行の例: `1: 敵のボディスラムが決まった / プレイヤーの張り手は外れた`
  - 相性で技が潰された場合も書く。
  - 過去のターンの行には、プレイヤーの入力文ではなく分類後の技名を使う。
  - 全ターン分を渡す。試合は 3〜6 ターン程度で終わるので、量は問題にならない。
- 数値（体力・ターン数・確率）を渡さない現行のルールと、`narratorRules` は維持する。
- 試合が決着した後に analyst が状況を更新したときも、勝者と決着の様子は従来どおり「この場面で描くこと」に入れる。

### 3. analyst への入力

analyst 向けの `situation()` に、敵の心境と敵の行動方針を加える。これで、`enemyTablePrompt` と `enemyMovePrompt` が敵の行動方針に沿って技を選ぶようになる。数値は従来どおり analyst にだけ渡す。

### 4. 文体（narrator の instructions）

- 語りは三人称で、プレイヤーに寄り添う視点にする。
- 地の文は短めにし、セリフを主役にする（セリフの多いライトノベル寄りの構成）。
- セリフはプレイヤー・敵・実況・解説の 4 者が話す。プレイヤーの心の声は `（）` で書く。
- 状況リストの心境と行動方針は、心の声とセリフの材料にする。ただし、プレイヤーの行動方針を、プレイヤーの入力より先に行動として描かない。
- 敵の心境と行動方針も narrator に渡す。敵は挑発や意気込みのセリフで気持ちを口にしてよいが、具体的な技名や次の一手は言わせない（`narratorRules` に 1 行足す）。`enemyPlan` は「距離を詰めて一撃で流れを戻す」程度の大まかな方針で、技名を含まないので、セリフに出てもネタバレにはならない。（実装側の判断）
- 400〜800 字と「数値を書かない」は維持する。セリフの割合は数値で指定しない。あとで差し替える文体見本と食い違わないようにするためである。

### 5. 文体見本（Few-shot）

- 新しいファイル `src/mastra/style-examples.ts` に置く。
- 「場面」と「結果」の入出力の例を 1 組ずつ用意する。入力側は、2 の新しい箇条書き形式で書く。
- narrator の instructions の末尾に「文体の見本（内容は真似せず、文体とセリフの比率だけを真似る）」として連結する。
- 見本の文章は仮のもので、ユーザーが差し替える前提である。差し替えやすいように、ファイルの先頭に「入力と出力の組を差し替える」と分かる形で並べる。

### 6. 処理中の表示（ユーザー決定 Q2=A）

- **サーバー:** workflow の各処理の開始時に `writer.custom({ type: "data-progress", data: { label } })` を流す。表示する処理名は次のとおり。

  | ステップ | 処理名 |
  |---|---|
  | setup | 「試合の設定を考えています…」 |
  | scene | 「敵の出方を考えています…」 |
  | resolve | 「技を判定しています…」 |
  | resolve（勝者が出たとき） | 「決着を決めています…」 |
  | resolve（状況の更新） | 「試合の流れを整理しています…」 |

  - 処理名だけを流し、決まった内容は流さない。
- **advance route:** `data-progress` を NDJSON の `{ type: "progress", label }` に変換する。
- **画面（`match-chat.tsx`）:**
  - 最新の処理名を 1 行だけ、今の「描写を待っています...」の位置に出す。
  - narration の `start` と `state` のイベントで消す。
  - 最後の吹き出しが narrator のときでも、処理名があれば表示する。結果の文章のあと、同じリクエストのまま次の場面の準備に入る間も表示するためである。
  - 処理名がまだ届いていない busy 中は、従来の「描写を待っています...」を出す。

### 7. 既存データ（ユーザー決定 Q3=A）

`data/app.db` と `data/mastra.db`（`-shm` と `-wal` を含む）を削除して作り直す。`data/auth.db` は残す。互換用のコードは書かない。

### 8. 画面に出す状態とデバッグ表示

- `toClientState` は、デバッグ表示が無効なときは `situation` も除く。敵の心境と行動方針がネタバレになるためである。
- narrate に渡す debug に、narrator へ渡したプロンプトの全文を加える。文体を調整するときに入力を確認できるようにするためである。

## 実装する人に任せること

- analyst への状況の更新指示の細かい文面と、各項目の文字数の目安。
- 「これまでの出来事」の 1 行の細かい言い回し。
- 処理中表示の見た目。既存の muted な文字の行を基本にする。
- テスト: 「これまでの出来事」の組み立てなど、純粋関数を 1 つテストする（`bun test`）。
